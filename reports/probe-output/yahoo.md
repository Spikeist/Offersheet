## Decisions

- Yahoo OAuth plan once YAHOO_CLIENT_ID / YAHOO_CLIENT_SECRET exist: 3-legged OAuth needs a browser and an HTTPS redirect, https://localhost:3000/api/auth/yahoo/callback (served by `npm run dev -- --experimental-https` once the Phase 5 route exists). Until then the probe does the browser-free steps: it writes the authorize URL to .cache\yahoo-oauth\authorize-url.txt (git-ignored; not printed because it contains the client ID), takes the code Parker copies from the redirect via YAHOO_AUTH_CODE, exchanges it once (no retries: codes are single-use) and writes YAHOO_REFRESH_TOKEN straight into .env.local without printing it. Later runs use the stored refresh token for a 1-hour access token, then look up the current NFL game key with game/nfl (never hardcoded): 200 = access is live, 403 = not enabled yet (probe once a day).
- Scope of this probe after approval: it verifies OAuth (consent → code → refresh token) and the current NFL game key only, and does not check items A–M. The Yahoo league checklist (league list via users;use_login=1/games;game_keys={game_key}/leagues, then league settings, teams/roster, standings, scoreboard;week={n}, transactions and players;status=A, with the Redactor registering team names, manager nicknames, guids, emails and image URLs) is Phase 5 work and still has to be written.
- The authorize URL sends only the parameters Yahoo's guide documents for request_auth (client_id, redirect_uri, response_type, state, language; DOCS.oauthGuide): no scope parameter. fspt-r ("Fantasy Sports: Read") is the API permission chosen when the app is created.
- Added YAHOO_AUTH_CODE and YAHOO_REFRESH_TOKEN for the manual OAuth steps; they are not in CLAUDE.md §0.5's variable list.
